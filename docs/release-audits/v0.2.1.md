# Release audit — v0.2.1

The evidence behind [the v0.2.1 release note](https://github.com/andrewmagness/webos-dispatcharr/blob/release/v0.2/docs/release-notes/v0.2.1.md). Written for a webosbrew reviewer, a contributor auditing an old release, and us in a year. The section at the bottom is generated from the artifact that was published; everything above it was written by a person before the release ran.

v0.2.1 is a patch on the `release/v0.2` maintenance line, cut from `main` at `503ed560`. Since v0.2.0 that adds one code change, #61 (`src/starfish.c`: release Feed's returned string), plus a host-side tool fix (#59, `tools/luna-sub.py`, not shipped) and documentation (#60, the v0.2.0 audit).

## Device test evidence

| | |
|---|---|
| television | LG OLED C1 (OLED65C1PUB), webOS 6.5.3 as the set reports it — the development set; exported-window video path |
| server | the owner's Dispatcharr server, v0.27.2, H.264/AAC channels; ESPN, 1280x720 at 60 fps |
| suite | `./tests/run.py` was not re-run for this release. #61 changes only how Feed's reply string is released after its verdict is read; the verdict, the payload and the pipeline the suite grades are unchanged |
| live | 2026-11-02, a debug build of the fix (`68cddf15`, identical `src/starfish.c` to #61) played ESPN for 40 minutes from launch, foreground, 60 fps by the heartbeat, with `feed abi: cxx11 … dtor=<resolved>` in the event log and the reply read as before (`{"returnValue":"Ok"}`) |
| memory | an on-set sampler read `/proc/<pid>/status` and `smaps` every minute. Before the fix (v0.2.0 code, same night, same channel) `[heap]` grew 9.2 → 18.7 MB over 40 minutes. After it, `[heap]` read 8.75 MB at start and 8.46–9.46 MB throughout. Mali GPU memory, threads (34) and descriptors (84) were flat in both |
| attribution | a diagnostic build (never merged; branch `diag/heap-scope`) interposed the allocator from the executable and tagged calls into libplayerAPIs: of the live heap that grew across a 12-minute window, the part inside `Feed` was `operator new` at one call site, 60,198 blocks (about 83 a second, about 33 bytes each). The host simulator, which runs the same demux and pump without libplayerAPIs, showed no growth under an `LD_PRELOAD` live-heap tracker |
| perf | heartbeat `fps=60` throughout on a `tvdev` deploy; no `ARM_PROFILE=release` frame-pacing measurement was made for this release |

The suite and the release-profile frame pacing were not run because the change is confined to the release of a returned string; the risk it carries is a wrong destructor, which would have faulted on the first Feed of the 40-minute run rather than degrade anything the suite measures.

## External compatibility reports known at release time

None from anyone outside the project. The owner ran v0.2.0 on the B8 (webOS 4.4.3) on 2026-10-31 and reported it performs well and the guide's corner picture works (#60).

## Compatibility tiers, and what moved

The C1 (webOS 6.5.3) stays verified, on this release. The B8 (webOS 4.4.3) moves to verified on v0.2.0 (owner report above) and has not run v0.2.1. It feeds through the same `sf_feed` (ACB only places its window), and its firmware family's libplayerAPIs exports the cxx11 Feed, so it took the same leak and takes the same fix — that is read from the code and the inventories, not measured on the set. The startup tier is unchanged: #61 adds two `dlsym` names and no link-time reference; in the inventories every libstdc++ beside a cxx11-Feed libplayerAPIs exports `_ZNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEED1Ev`, every libstdc++ exports `_ZdlPv`, and `tools/fwcompat.py` gave the same verdicts as v0.2.0's binary (OK from 3.4.0 up).

## Known issues at release, with provenance

- **MPEG-2 video and DTS audio.** As in v0.1.0's audit; nothing in this release touches either.
- **Memory growth — the steady part is fixed.** Root cause above; the v0.1.0 figure (about 7.5 MB an hour of whole-process RSS over 105 minutes, 2026-10-15) is this leak seen through RSS.
- **Memory after a reconnect.** In the pre-fix soak of 2026-11-02 the server ended the stream once (`demux ended`, one 503, reopened); anonymous memory outside `[heap]` rose about 22 MB across that and did not fall back. The access-unit queues are drained on teardown, so it is not those nodes; whether it is glibc keeping freed arena memory was not determined.
- **Thread-arena rise late in the post-fix soak.** `[anon]` rose about 5 MB (24.9 → 30.2 MB) over the last 12 of the 40 minutes, with no reconnect. The demux's access-unit queue swings between 3 and 9 MB on this channel; a high-water arena is the leading explanation and has not been confirmed. A two-hour soak is planned.
- **A Load keeps a 64 KiB slot for the process's lifetime**, by design: a late firmware callback carries only that address. Each channel change or reconnect therefore retains 64 KiB.

## Deliberately not done

- **No B8 run.** The second set takes installs on request and is not used for testing.
- **The reconnect and arena effects are not addressed** (above); they were measured, not attributed, and are named in the note.
- **Multiview** remains 0.3.0 work; nothing of it is in this build.
- **No crash reporting or analytics**, as in v0.1.0 (`docs/telemetry-removed.md`).

## Release configuration

|---|---|
| flavour | `com.magness.dispatcharrtv` (stable) — the id users install; `FLAVOR: stable` is pinned in the release workflow's build job |

| built by | GitHub Actions, from the tag, at a path identical on every runner |
| toolchain | webOS NDK as pinned by the workflow, Rust nightly pinned by date in the `RUST_NIGHTLY` repository variable |

Nothing unusual: no toolchain or dependency change, no new payload file, no new outbound host, and nothing written outside the app's own directory. The first release from a maintenance line; the tree carries a `RELEASE_LINE` marker (`0.2`) so a developer build of it reports the next patch.
