# v0.2.1 — long viewing no longer eats memory

Watching a channel for hours no longer makes the app use more and more of the television's memory. That growth, listed as unexplained in the last two releases, is found and fixed.

## Fixed

- **Memory grew for as long as a channel played.** Every piece of video and audio the app handed to the television left a small reply from LG's playback library behind in memory. At 60 frames a second that came to about 10–14 MB an hour, which is why a long session kept growing and why the growth stopped when a stream froze. The app now releases each reply. On the development set the memory the app allocates for itself stayed flat over 40 minutes of playback, where the same 40 minutes of 0.2.0 had grown it by about 9.5 MB.

## Compatibility

- **Plays video, verified by watching it — a 2021 LG set.** An LG OLED C1 (OLED65C1PUB) on webOS 6.5.3 is the development set: this release's fix was played there for 40 minutes at 60 frames a second against a real Dispatcharr server, with its memory sampled every minute.
- **Plays video, verified by watching it on v0.2.0 — a 2018 LG set.** An LG OLED B8 (OLED55B8PUA) on webOS 4.4.3 played live TV, and the guide's corner picture, with v0.2.0 (owner, 2026-10-31). This release has not been run on it. The changed code is on the path that set uses too, but its memory has not been measured there.
- **Starts, and nothing further is known — every other firmware from webOS 3.4.0 up.** The loader resolves this binary's libraries and symbols against all eleven firmware images webosbrew has at 3.4.0 or newer. That grades startup and says nothing about whether video plays; the matrix is in the [technical audit](https://github.com/andrewmagness/webos-dispatcharr/blob/release/v0.2/docs/release-audits/v0.2.1.md).
- **Does not start — webOS 2 and older.** Symbols the app needs are missing there, so the process is killed before anything appears.

If your set is in the middle two groups, [tell us what happened](https://github.com/andrewmagness/webos-dispatcharr/issues). It working is as useful a report as it failing.

## Known issues

- **MPEG-2 video channels do not play.** The television's buffer-feed pipeline does not accept MPEG-2 video; the app says so and suggests setting an H.264 stream profile for that channel in Dispatcharr. Unchanged from v0.1.0.
- **Some televisions cannot decode DTS audio.** The development C1 refuses a DTS stream, as many 2020-and-later LG sets do; such a channel needs an AC-3 or AAC audio profile in Dispatcharr. Unchanged from v0.1.0.
- **Memory may still rise somewhat after a stream reconnects, or over a session much longer than 40 minutes.** The steady growth is fixed, but two smaller effects seen on the development set are not yet explained: a stream that dropped and reconnected left about 22 MB more in use, and over the last minutes of the 40-minute check the memory behind the stream's read-ahead buffer rose by about 5 MB. Longer measurements are planned.

## Installing

Download **com.magness.dispatcharrtv_0.2.1_arm.ipk** and install it with the [Homebrew Channel](https://github.com/webosbrew/webos-homebrew-channel) or [dev-manager-desktop](https://github.com/webosbrew/dev-manager-desktop). You do **not** need a rooted TV.

Nothing in this distribution chain is signed, so this sha256 is what tells you the file you have is the file published here:

```
__IPK_SHA256__  com.magness.dispatcharrtv_0.2.1_arm.ipk
```

[Installing and checking a download](https://github.com/andrewmagness/webos-dispatcharr/blob/main/docs/install-and-verify.md) covers the other assets, how to check the hash on each platform, and the Developer Mode expiry that uninstalls your apps. This package bundles FFmpeg under LGPL-2.1-or-later and its complete corresponding source is attached to this release. Exactly what was built, verified and shipped is in the [technical audit for v0.2.1](https://github.com/andrewmagness/webos-dispatcharr/blob/release/v0.2/docs/release-audits/v0.2.1.md).
